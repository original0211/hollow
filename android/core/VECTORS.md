# 黄金向量版本管理口径（NP-1114-31 · 红队段内必改落字）

黄金向量是 Go 核心（第二实现）与 JS 规范实现之间的等价性锁。本文件定
向量的版本、生成与变更纪律；与本文件冲突的向量操作一律无效。

## 版本绑定

- 向量集按 **spec 版本**冻结：文件名 `testvectors/vectors-<spec版本>.json`，
  本批为 `vectors-v0.1.2.json`（对应冻结件 protocol-spec-v0.1.2.md）。
- 一份向量集只服务一个 spec 版本。spec 不变，向量集不变。

## 生成纪律

- 生成器 `testvectors/generate.mjs` 只许调用 JS 规范实现（`shared/`，
  D2 定案的 canonical 实现）与公开 RFC 测试向量；生成器源码与向量集同仓。
- 确定性：组件向量的输入全部是写死常量；会话 transcript 向量用真实
  JS 客户端↔JS 服务端对跑产生，随机量（临时密钥、随机数、填充）在
  生成后**回读记录**进向量文件，不靠种子复现（种子复现不了 WebCrypto
  的密钥生成；记录事实才是可复放的）。
- 原语层向量必须含**独立锚**且生成器在写入前先断言 JS 与锚一致、不过
  即中止：HKDF=RFC 5869 Case 1、HMAC=RFC 4231 Case 1（公布常数）；
  X25519=生成器内独立的 BigInt 曲线运算复算（不与 WebCrypto 同源）；
  ChaCha20-Poly1305=跨实现锚（JS/node 与 Go x/crypto 为两套独立实现，
  其一致性由 Go 侧逐向量断言本身构成——Go 原语若与 JS 产出不符，测试
  当场红，这正是该锚的执行点）。

## 变更纪律（重生成）

- 重生成只许随 **spec 变更流程**发生：新 spec 版本冻结 → 生成新版本
  向量集（新文件名）→ 变更记录登记（哪版 spec、为何重生成、向量 diff
  的审阅人）。无 spec 变更而重生成向量，是违规操作。
- **旧版向量集保留不覆盖**：新文件并存，Go 侧测试按当前冻结 spec 选集；
  历史集留作回溯与争议仲裁。
- **同版增补的唯一例外**：在红队/队长明示派单下，可在同一 spec 版本的
  向量集内**新增组**（如 NP-1114-34 的 recordsMulti），条件是再生后逐组
  比对证明既有组字节不变（transcript 组为实录会话、按设计刷新，不在
  此限，但须在回执中点名）；既有组的任何字节变动仍属重生成、仍须走
  spec 变更流程。
- 向量 diff 与代码同审：任何向量集的新增/变更进仓，红队须对 diff 本身
  过目（不是只看测试变绿）——向量就是判据，改判据必须有人看。

## 点名失效模式（红队原话，本口径的存在理由）

**「JS 改错、两边同错同绿」**：若有人把 JS 实现改错又顺手用错的实现
重生成向量，Go 实现会对着错误向量全绿——锁变成同谋。本口径的防线：

1. 重生成与 spec 变更流程硬绑定（上条），脱离流程的重生成在纪律上
   不成立、在评审上会被向量 diff 的人审拦下；
2. RFC 公开锚不依赖本仓任何实现：JS 与 RFC 不符时生成器当场中止；
   Go 侧另有直锚测试（TestRFCAnchorsDirect）把 RFC 5869/4231/8439 的
   公布常数硬编码在测试里、不经向量文件中转——Go 的原语先对 RFC、
   再对 JS，两句都是实测而非修辞（NP-1114-34 收口）；
3. 冲突仲裁顺序写死：**spec 文本 > RFC 锚 > 向量集 > 任一实现**。
   向量与 spec 不符时，错的是向量（或实现），不是 spec；按 spec 变更
   流程处理，不许反过来改 spec 就向量。
